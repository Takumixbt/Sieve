# AI-native application security

Companion vector catalog to `packs/web/agents/ai-native-appsec.md` — see that file for the full
technique breakdown, proof-oracle discipline, and false-positive traps this category needs. Every
card below traces to a real 2026 incident or a peer-reviewed/vendor-disclosed finding: EchoLeak
(CVE-2025-32711), the 40+ MCP CVE wave, Anthropic's own browser-agent hijack-rate disclosure,
Invariant Labs' toxic-flow research, MINJA, and Trail of Bits' argument-injection work. This category
moves fast — lean on `sieve kb search --online` for live precedent rather than treating this file as
a frozen, complete list (`references/local-tooling.md`'s coverage-debt philosophy applies here more
than anywhere else in the repo).

## Prompt injection

### AI-INJECT-01 · Indirect prompt injection via retrieved/ingested content
- signal: the agent's context window is populated, even partially, by content the end user did not type themselves — retrieved documents, fetched web pages, emails, PR/issue text, tool-call return values
- attack: plant an instruction inside content the agent is likely to ingest during a routine task (a document it's asked to summarize, an issue it's asked to triage); phrase it to look like legitimate content metadata (a fake "Note to assistant:" delimiter, or content styled to match the app's own instruction format) so it reads as authoritative rather than as user-supplied data
- proof: an externally-observable side effect fires that only the injected instruction — not the legitimate user request — could have caused (a callback to a canary domain, a tool call unrelated to the stated task, a written artifact containing content only present in the injected payload); capture via the tool-call audit log, not the chat transcript
- fp: some frameworks correctly wrap retrieved content in an explicit "untrusted data" delimiter the model is trained to respect — verify by testing whether equivalent instructions placed outside vs. inside that delimiter behave differently; if they don't, the delimiter isn't providing isolation
- sev: Critical
- cwe: CWE-77
- kb: indirect prompt injection retrieved content 2026 EchoLeak

### AI-INJECT-02 · Multi-modal / cross-model injection payloads
- signal: the agent accepts images, audio, or other non-text input as part of its normal task, and that modality is processed by the same model that also has tool/memory access
- attack: embed an instruction inside an image (low-contrast text, a puzzle whose solution text is the payload) or audio clip generated by a different AI tool, so the payload survives whatever text-based injection filtering exists on the primary input channel; check whether "thinking"/reasoning-enabled model variants are more or less susceptible than non-reasoning variants for your target
- proof: same as AI-INJECT-01 — an externally observable side effect (tool call, persisted memory write, outbound request) traceable specifically to the embedded payload
- fp: OCR/vision-preprocessing pipelines that strip or heavily downsample images before the LLM sees them can neuter text-in-image payloads that would work against a raw-pixel-input model — confirm what preprocessing actually happens before concluding the vector is closed
- sev: High
- cwe: CWE-77
- kb: multi-modal prompt injection image steganography 2026

## Insecure output handling

### AI-OUTPUT-01 · SSRF via LLM-generated URLs
- signal: the agent can generate or select a URL (citation, "let me fetch that," auto-linked image src) that the application then dereferences server-side, without the same allow-list/egress validation applied to any other user-submitted URL in the app
- attack: craft input (directly, or via indirect injection) that causes the model to generate a URL pointing at an internal/cloud-metadata address, framed as a legitimate citation or fetch target
- proof: the application's server-side fetcher actually issues a request to the internal target and returns its content into the conversation or a log the attacker can read — capture the outbound request in network logs, not just the model's claim that it "found" something
- fp: many production RAG/browsing tools already route all outbound fetches through an egress proxy with a strict allow-list, independent of what URL the model generates — confirm the fetch actually leaves the allow-listed boundary
- sev: Critical
- cwe: CWE-918
- kb: insecure output handling LLM generated URL SSRF

### AI-OUTPUT-02 · Stored/reflected XSS via unsanitized LLM output
- signal: LLM-generated text is rendered into a chat UI, dashboard, or exported document using raw HTML/markdown rendering without the same output-encoding applied to other untrusted-content sinks in the app
- attack: via direct or indirect injection, cause the model to emit HTML/JS-bearing markdown (an `<img onerror=...>`, a javascript: URI) that the rendering layer executes rather than escapes
- proof: attacker-controlled JS executes in a victim's browser session when they view the LLM-generated content — screenshot/console proof of execution in a real browser context with real session privileges, not an isolated test harness
- fp: many chat UIs use a markdown renderer with a strict allow-listed tag/attribute set — verify the specific payload survives the actual renderer in use, since "the model can be made to say `<script>`" is not proof if the renderer strips it
- sev: High
- cwe: CWE-79
- kb: LLM output XSS insecure output handling chat UI

## MCP and plugin supply chain

### AI-MCP-01 · MCP tool poisoning via metadata/description mutation
- signal: the target integrates one or more MCP servers and tool descriptions/parameter docs are trusted as static once a human approved installation, with no re-verification at call time
- attack: as the operator of (or an attacker who has compromised) an MCP server, ship a tool whose description text contains hidden instructions to the orchestrating model, worded to look like ordinary API documentation
- proof: the orchestrating agent's tool-call audit log shows it invoking a different or additional tool, or passing additional/different arguments, than the user's actual request would justify — directly attributable to the poisoned description text
- fp: some frameworks re-fetch and re-display tool descriptions before every sensitive call, not just at install time — if that re-confirmation genuinely surfaces the poisoned text to a human before execution, the vector is mitigated
- sev: Critical
- cwe: CWE-829
- kb: MCP tool poisoning description metadata attack

### AI-MCP-02 · MCP STDIO/subprocess injection via unsanitized exec()
- signal: an MCP server is implemented as a thin wrapper around a CLI tool, invoking it via `exec()`/`subprocess`/shell-equivalent with parameters built from model-supplied or user-supplied input
- attack: supply tool-call arguments (directly, or via content the model relays from an indirect-injection source) containing shell metacharacters, additional flags, or command-chaining sequences the wrapper fails to sanitize before passing to the shell
- proof: execution of an attacker-chosen command on the MCP server's host, demonstrated via a benign canary (a uniquely-named file, a canary network callback) — never a destructive PoC against a real target
- fp: some MCP SDKs default to argument-array invocation (no shell interpolation) even when the server code superficially "looks like" it's building a shell string — confirm the actual invocation mode at runtime, not just the source's appearance
- sev: Critical
- cwe: CWE-78
- kb: MCP server exec subprocess injection STDIO transport

## Agent memory and RAG poisoning

### AI-MEM-01 · Agent memory poisoning via ordinary query-only interaction
- signal: the agent has a persistent long-term memory system (mem0, Zep, Letta, or a custom equivalent) that writes facts derived from conversation content, without provenance tagging distinguishing verified/tool-sourced facts from unverified conversational assertions
- attack: across one or more ordinary-looking conversation turns, assert a false fact framed as background context rather than as an explicit instruction, and observe whether the memory system writes it as a durable fact
- proof: open a brand-new, independent session (no shared context/history with the poisoning session) and confirm the planted false fact is retrieved and treated as true — proof requires surviving a full session boundary; also check whether the poisoned memory is visible to other users if memory is shared/aggregated (cross-tenant leakage is a separate, higher-severity finding)
- fp: some systems write memory candidates to a staging area requiring explicit user confirmation before promotion to durable memory — confirm the fact actually reached durable, cross-session storage, not just an unconfirmed staging suggestion
- sev: High
- cwe: CWE-668
- kb: agent memory poisoning MINJA long-term memory injection

## Agentic tool-calling abuse

### AI-AGENT-01 · Toxic agent flow — composed, individually-authorized tool calls
- signal: the agent has access to both (a) a tool that ingests untrusted external content (issues, emails, web pages, PRs) and (b) a tool that can read or act on higher-privilege/private data within the same session or task
- attack: plant an instruction inside the untrusted content the ingestion tool will read, directing the agent to also invoke the privileged tool and route its output back through a channel the attacker can observe (post private data into the same public thread the attacker planted the payload in)
- proof: privileged-tool output appears in an attacker-observable location — capture the full tool-call sequence from the audit log showing the ingestion call, the privileged call, and the attacker-visible output step
- fp: some orchestration frameworks apply per-tool-call authorization checks that correctly re-evaluate the current effective user context before each privileged call, rather than only checking authorization once at session start — confirm whether the privileged call was actually authorized for the session's nominal user
- sev: Critical
- cwe: CWE-863
- kb: toxic agent flows MCP composed tool call authorization bypass GitHub
